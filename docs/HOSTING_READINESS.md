# Hosting decisions and readiness

The Flutter app and Rust API already exist. Hosting provider, server and domain are intentionally undecided. Nothing in this change provisions infrastructure, changes DNS, buys a domain or publishes the app. Keep this extension separate from CE7454 submission files.

## Portable starting architecture

Use one HTTPS origin for the web app and Rust API: Caddy serves the Flutter bundle and proxies `/api/v1/*` and `/healthz` to Rust on loopback port 8787. This works on a suitable Linux VM, not only EC2. The existing `docker-compose.ec2.yml` is a Linux host-networking template; managed containers and macOS Docker require their own networking adaptation. Existing systemd units require Tailscale, so review that dependency for a symbolic-only installation.

Web builds now default to the page's origin, so a single bundle can move from staging to the final domain without rebuilding. Explicit `API_BASE_URL` overrides this for split hosting. Native Android/iOS builds still need the selected HTTPS API URL at build time; the development default remains loopback. Local `flutter run` on a different port needs the explicit localhost API URL shown in the README.

## Decisions to fill in later

- Server: provider, region, Linux distribution, CPU architecture, budget and operator.
- Public hostname: one application hostname is simplest. Choose registrar/DNS owner and staging hostname; no domain is reserved yet.
- Access: private team demo versus public distribution. CORS is not authentication. A shared token compiled into Flutter Web or mobile can be extracted and is not a production user-authentication system. Use an access gateway or real user sessions before public GPU access; keep worker credentials server-side only.
- GPU: machine, private Tailscale endpoint, model/fixture provenance and verified real inference readiness. Leave MODEL_WORKER_URL and MODEL_WORKER_TOKEN empty until selected. Symbolic mode remains usable without a worker.
- Operations: TLS renewal, ingress firewall, rate limits/quotas, health monitoring, logs/redaction/retention, update ownership and rollback version. Do not log meal preferences or authorization headers.

## Configuration contract

| Setting | When to choose it | Boundary |
| --- | --- | --- |
| DOMAIN | After hostname selection | Required by Compose/Caddy; no example-domain fallback |
| APP_BIND_ADDR / APP_PORT | Server networking | Default 127.0.0.1:8787 behind TLS proxy |
| APP_ALLOWED_ORIGINS | After web hostname selection | Exact trusted origins; no wildcard for private demo |
| APP_API_TOKEN | With access design | Prototype shared access only; never a substitute for per-user auth |
| API_BASE_URL | Native build or split-origin web | HTTPS selected endpoint; omit for same-origin web |
| MODEL_WORKER_URL / TOKEN | After private GPU setup | Server-side only; empty means symbolic-only |

Copy deployment env templates locally only when configuring the chosen host. `deploy/env/*.env` is ignored by Git. Do not commit credentials. Example client tokens must be replaced or deliberately removed for a private symbolic demo; they are not usable secrets. No credentials are generated by this readiness work.

## Build now, deploy later

From the extension root:

```sh
./deploy/predeploy-check.sh
cd mobile
flutter build web --release --no-web-resources-cdn
# Later, after choosing the native client's server:
# flutter build apk --release --dart-define=API_BASE_URL=https://<chosen-host>
```

The local gate verifies code/build behavior and a **dry-run** worker contract only. It does not establish live model quality, swallowing safety, actual DNS/TLS, server security or production readiness. Review `DEPLOYMENT.md` as an EC2-specific option, not a selected provider or promised rollout date.

Before launch, validate the chosen host configuration, DNS and certificate, access controls, allowed/denied requests, API connectivity from a real device, resource limits and a worker outage. Run an actual GPU inference with provenance before claiming the model is connected. Preserve a prior release for rollback. Deployment and distribution remain separate authorized actions.
